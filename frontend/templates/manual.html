操作手册

第一章「连通性与鉴权」的用例定义、平台自动化范围与需人工执行的步骤。

返回接口测试

执行流程

WORKFLOW
  1. 准备端点与凭证：填写供应商基础地址、完整协议路径前缀、有效 Key、错误 Key 与拟上架模型 ID。
  2. 确认链路：先测上游直连，再测转发链路；两条链路分别独立判定，不能互相替代。
  3. 运行验收套件：默认每模型每条链路连续 3 次普通请求 + 3 次流式请求，鉴权与模型边界用例各 1 次。
  4. 处理 FAIL：先看证据中的状态码与错误码，再决定重测、换模型或联系供应商；补跑单次成功不能替换失败记录。
  5. 留存记录：导出 Markdown / CSV，与供应商沟通记录、上游日志一并归档。

判定口径：某模型通过不代表其他模型通过；某条链路通过不代表另一条链路通过；某个协议通过不代表其他协议通过。

平台自动化的边界

SCOPE

以下用例需要供应商控制台或平台侧配置权限，平台只能记录人工结论，不会伪造通过结果：

  • AUTH-05 已撤销 Key：需在供应商控制台创建并撤销测试 Key，记录撤销生效时间。
  • MODEL-05 权限边界：需供应商侧模型级权限与受限 Key。
  • AUTH-06 / AUTH-07 / AUTH-08 已于 2026-10-24 升为自动：「有返回即通过」「声明与实发鉴权头一致」「目标模型可用」都可直接判真假，见下方 1～4.2 自动行。
  • MODEL-04 转发映射：需对照 Fluxlane 渠道日志确认实际选中的上游模型。
  • TIME-02 / TIME-03：需要可控模拟上游；平台已附带 tools/mock_upstream.py。
  • Claude 固定回归（Go 套件 tests/anthropic_channel_accept_test.go）不在本平台内实现，仍需在代码仓库执行。

用例定义

CHAPTER 1

1.0 前置必测（GATE）

编号测试方法通过标准平台执行
GATE-011 次非流式（须返回 G1_OK）+ 1 次流式（须有内容且正常结束）两次都正常才通过；任一次失败、被截断或未返回 G1_OK 即不通过自动（优先执行）
GATE-02先由第 1 次请求写入缓存（Claude 用 cache_control，约 3000 token 前缀），再用相同输入连发 5 次首次写入不计；后 5 次必须全部命中（命中率 = 1）；未返回缓存用量字段按未命中计自动（优先执行）
GATE-03连发 20 次相同短输入，逐次记录耗时并计算 P5 / 中位 / P9520 次必须全部成功且中位 ≤ 10s；任一次失败或中位 > 10s 不通过（分位随任务保存作渠道权重）自动（优先执行）

1.3 端点与网络连通性（NET）

编号测试方法通过标准平台执行
NET-01从实际测试机解析供应商域名，记录解析结果域名可正常解析，无持续性解析失败自动（dig）
NET-02通过正常 HTTPS 校验连接端点，不关闭证书校验TLS 握手成功，证书有效且与域名匹配自动（复用首个请求）
NET-03使用文档规定的完整路径发送最小有效请求请求到达正确 API，无路径重复、404 或网页自动
NET-04不跟随重定向发起一次请求，只检查状态码状态码不是 3xx自动
NET-05从实际运行环境发起同类请求运行环境可访问，不以个人电脑测试成功为结论平台即运行环境

1.4 普通请求（REQ）

编号检查内容通过标准
REQ-01HTTP 状态码及响应体返回协议约定成功状态，响应体可解析
REQ-02模型是否输出与提示词相符的内容返回有效文本，不为空、仅空白或只有元数据
REQ-03请求是否完整结束在总超时预算内返回完整响应，无持续挂起
REQ-04Content-Type 与实际内容返回 API 数据，不得是登录页、验证码页或代理错误页
REQ-05请求模型、配置映射与上游日志路由到目标模型与渠道；model 字段差异有明确映射说明

执行方法：每个拟上架模型，在两条链路上分别连续发送 3 次非流式请求。

1.5 流式请求（STREAM）

编号测试方法通过标准
STREAM-01开启流式参数，检查响应头与事件格式按约定协议返回流式响应，无解析错误
STREAM-02从请求发出计时，记录首个实际内容到达时间在首个有效内容预算内收到内容
STREAM-03持续读取事件并拼接正文得到有效回答，无空流或仅心跳
STREAM-04检查协议结束事件/标记与连接收尾收到正常结束信号，并在总超时内完成
STREAM-05流开始前后的错误能否被识别不得把错误事件或异常断流当作正常成功

首内容计时不含 HTTP 响应头、SSE 心跳与空事件；平台按内容增量计时。

1.6 鉴权（AUTH）

编号测试场景通过标准平台执行
AUTH-01有效 Key请求成功自动（复用 REQ）
AUTH-02缺少鉴权头明确拒绝，无模型输出自动
AUTH-03鉴权值为空明确拒绝，无模型输出自动
AUTH-04格式合理但随机的错误 Key明确拒绝，无模型输出自动
AUTH-05成功后撤销专用 Key在声明生效时间内被拒绝人工
AUTH-06用无效（等价过期）Key 发起请求只要有 HTTP 返回即通过（是否明确拒绝由 AUTH-04 判）自动
AUTH-07比对声明的鉴权方式与请求实际发出的鉴权头一致即通过，不一致不通过自动
AUTH-08用提供的 Key 请求目标模型2xx 且有正文即通过自动
AUTH-09已禁用的平台 Key平台拒绝且不向上游发起调用人工（Fluxlane 侧）

1.7 模型 ID 与权限边界（MODEL）

编号测试方法通过标准
MODEL-01对清单中每个拟上架模型分别请求所有模型均可用，单个成功不能代替其他
MODEL-02请求明确不存在的模型 ID返回明确错误，不得静默改用默认模型
MODEL-03修改模型 ID 一个字符或使用未配置别名返回明确错误；支持别名需记录映射
MODEL-04通过对外 ID 请求，核对实际渠道与上游 ID映射正确，日志可关联目标渠道
MODEL-05受限 Key 请求未授权模型平台拒绝，不绕过模型限制调用上游

1.8 超时与失败返回（TIME）

编号测试方法通过标准
TIME-01隔离配置中使用不可达端点在连接超时预算内失败，错误可识别
TIME-02模拟端点接受连接但不返回内容在首内容或总超时预算内结束
TIME-03模拟端点仅发送心跳或空事件心跳不能使请求无限存活
TIME-04请求发出后主动取消客户端及时退出，平台停止读取并记录取消

1.9 记录字段

每条用例至少记录：测试对象（供应商、渠道、协议、模型 ID）、测试链路、用例编号、带时区的执行时间、执行结果（PASS / FAIL / 不适用 / 未执行）、响应信息（状态码、脱敏错误、请求 ID）、耗时（连接、首内容、总耗时）、定位证据。平台的导出文件已按该结构组织。

不得为测试而撤销生产 Key；模拟端点只用于验证平台超时与取消机制，不能据此宣称供应商具备相同行为。

自动验收任务

AUTO TASK

1. 新建任务

进入「自动验收」页，填写接口 Base URL、API Key、模型 ID，选择接口协议（不确定时点「识别」， 平台会探测 /models；仍无法确定时必须手动选择，不会猜测）。其余参数有默认值，一般无需修改。

  • 「该端点无需鉴权」仅用于确实不校验凭证的私有化端点。
  • 「同时测试 Fluxlane 转发链路」需要填写真实转发地址与 Key；不填就只跑直连， 报告里会明确写「测试链路 = 上游直连」，不会把直连结果当成转发结果。
  • 「最大请求数 / 最大时长」是任务预算，用尽后不再发请求，剩余项记为未测试。

2. 执行与查看

任务在后台执行，页面每 3 秒刷新进度；关闭页面或重新登录后仍可继续查看。 执行顺序固定为第一章 → 第二章 → 第三章 → 第四章；第一章关键项全部未通过时， 后续章节直接标「阻塞」，避免继续产生费用。

3. 人工确认与证据

无法自动判定的测试项状态为「待确认」。在测试项行点「人工确认」，填写实际结果与说明， 可附一张 ≤ 2 MB 的截图/日志/PDF；平台记录上传人、时间与文件 SHA-256，PDF 报告第六节会列出。 标记「不通过 / 不适用 / 阻塞」时必须填写说明。

4. 重测

  • 单个自动项：「立即测试」，需重新输入 API Key，旧判定写入重测日志。
  • 某一章 / 整个任务：「重测某章」「重测整个任务」，会创建新任务并保留原任务记录。
  • 第一章用例依赖整批执行状态，只能按章或整任务重测。

5. 凭证

API Key 只在任务执行期间存在于服务端内存，任务结束、取消或异常时立即清空； 不写数据库、不写日志、不写报告，页面也没有任何接口可以读回原始 Key，所以重测时必须重新输入。 服务重启后运行中的任务会标记为「已中断」，不会用残留凭证继续执行。

第 1～4 章与 PDF 报告

CHAPTER 1–4

1～4.1 标准从哪里来

第一章「连通性与鉴权」共 36 个用例：原文 33 个（NET 5、REQ 5、STREAM 5、AUTH 9、MODEL 5、TIME 4） 已按原文 1.3–1.8 的用例表建立结构化定义，编号与验收套件完全一致，由套件真实执行； 另有 3 条平台新增前置必测（GATE-01 连通性（非流式 + 流式）、GATE-02 缓存命中率、GATE-03 延时分位）， 优先执行，任一不通过即直接判不达标，不再执行后续测试。 第 2～4 章（接口兼容性、缓存正确性、模型与能力真实性）的用例表以 Excel 对象嵌入原文， 原文以 33 张内嵌 Excel 表（Worksheet9–41）为载体，平台按文档流顺序解析出 133 个测试项，其中有测试项的表为 23 张。两部分的测试方法、通过标准与章节归属都不可修改。

1～4.3 判定与版本

  • 单项状态：通过 / 不通过 / 未测试 / 待确认 / 标准未定义 / 不适用；没有记录的一律是“未测试”，不会默认通过。
  • 第一章同一用例在直连与转发链路上各执行一次，判定取最差结果：任一条链路不通过即为不通过。
  • 整体结论：任一不通过 → 不达标；存在未测试/待确认/标准未定义 → 无法判定；全部适用项通过 → 达标。
  • 修改标准（启用状态、必测级别、供应商侧参数）会生成新版本；历史批次仍绑定原版本，报告不受影响。
  • 原文要求按供应商配置的参数（缓存最小长度、TTL、上下文长度、最大输出）未填时，相关项显示“标准未定义”，不计入通过。

1～4.4 导出 PDF 报告

在“验收记录”选中批次 → 查看整体结论与逐项状态 → “导出 PDF 报告”。 报告含报告编号、被测对象、标准版本与校验值、分章汇总、第一章执行记录、逐项预期/实际/判定、问题清单与限制说明，页脚有页码。 导出时后端会重算判定并校验标准快照，未绑定标准的批次、标准校验不一致或无权访问的记录都会被拒绝并给出原因。 若批次绑定的标准版本早于第一章合并，报告仍会列出当时的用例执行记录，但标注“不参与本次结论”。 报告中不含 AK/SK、API Key、Authorization 头或 Cookie。
